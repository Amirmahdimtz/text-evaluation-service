# Stage 11 — Pragmatic Production-Grade Baseline (2026-10-31)

> **Status:** `PROPOSED_ENGINEERING_BASELINE / NOT_DEPLOYMENT_APPROVAL` · applies to Stage 11 only, before Stage 12. This document records the user's preference for **a useful, standard, maintainable product without unjustified complexity**. The preference is confirmed; specific security/data/quality/service-level choices below are **recommendations pending the appropriate deployment owner or business decision**. It does not supersede confidentiality, the approved architecture guide, the implementation plan's mandatory Stage11 gate, or existing 56 deferred test IDs.

## 1. Product objective and decision rules

The service must evaluate confidential Persian text for `speech`, `media` and `research`, entirely on authorized internal infrastructure. It must return versioned rubric-aligned assessments, grounded quote/offset evidence, conservative abstention and deterministic Python-calculated scores, with a durable API/Worker/PostgreSQL workflow, scoped authorization and reproducible results.

**Default: use the simplest design that passes these properties and its measured workload.** Reuse existing FastAPI, PostgreSQL async, local vLLM, `LocalLlmProvider`, `SignedIdentityVerifier`, `EncryptedContentService`, `SecretResolver` and durable `EvaluationWorkerService`. Follow `Host → Application → Core → Infrastructure`, constructor DI and existing repositories. Avoid new queues, databases, orchestration clusters, IAM services, KMS/Vault adapters, interfaces, admin portals or observability stacks without an actual requirement or an observed failure.

**Non-negotiable:** no external text inference/data/telemetry, fail-closed auth and organization ownership, encrypted confidential text/results, protected secrets, authenticated interfaces, no sensitive logs, artifact/licensing checks, reliable retries/restore, real AI quality measurements, documented rollback/backup and real Stage11 acceptance evidence. “Simple” never means disabling safeguards.

**Approval distinction:** `D-015` defers formal employer/SME **business sign-off** to Stage 12. Stage 11 still requires **operational authorization before protected environment/network/GPU/secret operations**, and real test evidence. Do not demand six separate formal business signatures for a harmless offline regression; where organizational policy allows, one accountable staging owner can authorize a bounded synthetic test and coordinate specialist reviews. Only actual privilege/data/network rights may be exercised.

## 3. Minimum deployment shape — recommended, not yet configured

```text
Internal authorized client
    -> existing trusted TLS gateway / short-lived signed JWT
    -> FastAPI (scope-enforcing)
    -> PostgreSQL (encrypted source, scoped jobs, rubric snapshots, audit)
    -> 1 bounded Worker (approved decrypt/execute, durable claim/fencing)
    -> existing on-prem vLLM container (only internal allowed access)
    -> validated evidence/offset + deterministic Python scoring
    -> encrypted report visible only to authorized requester/reviewer
```

- **One host / Docker-based installation can be Production-Grade for an appropriately modest workload**, if isolation, reliability, backups, monitoring, network controls and recovery objectives **actually pass**. Kubernetes, service mesh, high availability clusters and microservices are not a default condition. If strict HA is mandatory, single-node deployment is insufficient; then design HA based on the requirement.
- The current `appsettings.yaml` explicitly has `llm.enabled=false`, `worker.enabled=false`, `http_security.enabled=false`. This is a safe guard, **not a feature toggle to bypass** without proper configuration and integration. The Host Worker currently rejects unapproved executors.
- Preserve development-only safeguards; design an explicit approved staging/production composition root and secure configuration rather than weakening fail-closed checks.
- Never send actual private texts, model identities, network details, keys or raw log evidence into this **public GitHub** repository or chat.

## 4. Acceptance simplification without waiving requirements

- **Retain all 56 original mandatory Stage11 test IDs.** They need not imply **56 separate commands or meetings**: one authorized test run can substantiate multiple IDs **when each ID has an independent assertion, result, owner and evidence reference**. A single smoke roundtrip does not satisfy deeper security, quality or recovery criteria.
- Cluster actual execution into **five evidence packages**: (1) approved environment + provenance; (2) real model and labeled Persian quality; (3) authenticated/encrypted protected E2E; (4) No-Egress and privacy negatives; (5) bounded capacity/recovery/operability. Preserve traceability to every original test ID and report individual PASS/FAIL/BLOCKED.
- **Mandatory vs conditional:** authenticated access, confidential-data encryption, private inference/no-egress, reproducible approved artifacts, correct quote and score validation, tested restores and source-to-report E2E are mandatory. Dedicated Vault/KMS product, dedicated SSO implementation, Kubernetes, distributed tracing, per-hop mTLS on a documented same-host trust boundary, multiple GPUs and weeks-long soak are conditional on approved policy/risk and measurable workload.
- **No arbitrary new acceptance bars.** Numeric settings in this document are `PROPOSED_STARTING_VALUES`, not `PASS` thresholds. `OD-03/04/07/08/09/12/13/14` remain open until their accountable owner accepts a value and records an effective version.
- **Two-model comparison is still present in the existing implementation plan** and is **not silently removed**. To waive/replace it, revise that Gate through an explicit recorded decision, supported by resource and licensing evidence.
- The employer/SME consolidated business sign-off stays at **Stage12** per `D-015`; internal technical approval for privilege/data/security test execution is separate. A single accountable owner may coordinate multiple technical roles when allowed by policy; do not invent organizational approvals.
- `Stage11=DONE` only after real acceptance evidence satisfies the unchanged Gate; `Stage12` remains `NOT_STARTED` until separately requested.
